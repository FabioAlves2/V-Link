# V-Link Roadmap

Development plan for what comes next, past the current MVP. Ordered so each milestone builds on a stable foundation before adding more surface area: harden what exists → give promoters real tools → give volunteers a richer experience → ship it.

## Milestone 1 — Harden the MVP

Foundation work before adding more surface area on top of it.

- [x] Add bean-validation annotations (`@Valid`, `@NotBlank`, `@Size`) on DTOs and `Event`, replacing the ad-hoc `@PrePersist` date checks with proper validation errors
- [x] Add a real test suite: backend (`@SpringBootTest`/`MockMvc` for controllers, unit tests for `JwtUtil`/repositories), frontend (Vitest + React Testing Library for at least the auth flow and event list)
- [x] Add a `POST /auth/logout` / token-revocation mechanism (tokens currently can't be invalidated early)
- [x] Move from `ddl-auto: update` to Flyway migrations (works for both H2 dev and Postgres prod), so schema changes are explicit and reviewable
- [x] Add rate-limiting/lockout on `/auth/login` (no brute-force protection today)
- [x] Implement the draft/publish workflow properly — event creation currently always forces `PUBLISHED`; add a way for promoters to save a draft and publish later
- [x] **Milestone review**: confirm every task above is checked off; re-read the milestone against the current code and note anything that needs to change before moving to Milestone 2

  **Review notes (2026-08-06):** All six tasks shipped and verified (backend: 16 MockMvc/unit tests; frontend: 4 Vitest/RTL tests; manual curl walkthrough of the full draft→publish→subscribe→logout flow against a fresh H2 instance). Implementation choices, scoped down from the broadest possible version of each task:
  - **Logout** revokes only the refresh token (new `RefreshToken`/`jti` table); the already-issued ≤15-min access token keeps working until natural expiry — no per-request revocation check was added, so `JwtAuthFilter` stays stateless. Full immediate revocation would need a denylist checked on every request.
  - **Rate limiting** is a hand-rolled in-memory `ConcurrentHashMap` in `LoginAttemptService` (5 failures/15 min per email), not a library — fine for the single-instance deployment target, but won't survive a restart or scale past one instance without moving to something shared (Redis) once Milestone 4's deployment target is decided.
  - **Draft/publish** has no dedicated UI for a promoter to find their own drafts again — `CreateEvent.jsx` can save as draft or publish directly, and `EventEdit.jsx` can change status, but there's no listing of "my events" yet. That's explicitly Milestone 2's Organizer Dashboard; nothing here needs to change, just noting the dependency.
  - **Flyway** baseline (`V1__init.sql`) was hand-written to match Hibernate's prior auto-DDL rather than generated, since ddl-auto had to switch to `validate` in the same step — verified by a fresh boot against wiped H2 with no `SchemaManagementException`.
  - Nothing discovered here changes Milestone 2's scope as written.

## Milestone 2 — Organizer tools

Promoters currently have no way to manage what they've created beyond the create/edit forms.

- [x] **New page: Organizer Dashboard** — list of events created by the logged-in promoter, with subscriber counts and quick edit/close links
- [x] **New page: Event Subscribers view** — per-event list of volunteers who signed up (name/email), with CSV export
- [x] Feature: event image upload (replace the current URL-only field) — needs a storage backend (local disk to start, or S3-compatible later)
- [x] Feature: close/cancel an event, notifying already-subscribed volunteers (in-app notifications — no email infrastructure exists until Milestone 3)
- [x] Feature: attendance/check-in tracking — mark which subscribers actually showed up (foundation for volunteer-hours tracking in Milestone 3)
- [x] Seed a subscribed (and checked-in) volunteer in `BootSeed.java`'s dev data, so the dashboard/subscribers/attendance UI have non-empty data to click through on a fresh H2 instance
- [x] **Milestone review**: confirm every task above is checked off; re-read the milestone against the current code and note anything that needs to change before moving to Milestone 3

  **Review notes (2026-08-07):** All five feature tasks plus the seed-data addition shipped and verified (backend: 20 new/extended MockMvc tests across `EventControllerTest`, `EventSubscriberControllerTest`, `NotificationControllerTest`, `EventImageUploadTest`; frontend: 6 new Vitest/RTL tests; a full Playwright walkthrough against the real dev servers covering dashboard → subscribers → attendance → CSV export → image upload → close → volunteer notification). Implementation choices, scoped down from the broadest possible version of each task:
  - **Notifications** are a new `Notification`/`is_read` table populated only on a PUBLISHED→CLOSED transition, one row per subscriber — no push/email, just a polled (30s) unread-count badge and dropdown in the Navbar. Still no per-request access-token revocation or any other Milestone-3-adjacent infra was pulled forward.
  - **Attendance** added `checked_in`/`checked_in_at` to `subscriptions` via `V4__subscription_checkin.sql`. H2 (in `MODE=PostgreSQL`) rejected a single multi-column `ALTER TABLE ... ADD COLUMN a, ADD COLUMN b` statement that Postgres itself would accept — split into two separate `ALTER TABLE` statements for cross-DB safety; worth remembering for any future multi-column migration.
  - **Image upload** is local-disk only (`app.upload.dir`, default `./uploads`), served publicly via a `/uploads/**` static resource mapping — no auth on the images themselves since the events they belong to are already public data. `EventEdit.jsx` uploads immediately on file selection; `CreateEvent.jsx` defers the upload until after the event is created (needs the id first) as a deliberate two-request sequencing tradeoff.
  - **CSV export** is fully client-side (`utils/csv.js`, `Blob` + temporary `<a download>`) against the already-fetched subscriber list — no dedicated backend endpoint, since the app's scale doesn't justify one.
  - **Organizer Dashboard** is a new `GET /events/mine`, scoped server-side to the authenticated promoter's own email, returning all statuses (including drafts) — distinct from the public `GET /events` list, which stays hardcoded to `PUBLISHED` only.
  - Confirmed the pre-existing logout-redirects-to-`/login`-instead-of-`/` bug (noted in `CLAUDE.md`, predates this milestone) is still present and unrelated to any Milestone 2 change — still not fixed, pending explicit direction.
  - Nothing discovered here changes Milestone 3's scope as written.

  **Post-milestone fixes (2026-08-07):** A run of user bug reports plus a deliberate use-case sweep reworked the event lifecycle and closed several real gaps, each shipped with tests confirmed to fail without the fix and pass with it:
  - **Close vs. cancel split.** "Encerrar" was covering two different situations (ending something running vs. something that was never going to happen), which is why the volunteer-facing status chip couldn't reliably tell them apart. Split into "Encerrar" (`PUT status:CLOSED`, only once started, notifies, preserves history permanently) and "Cancelar" (`DELETE /events/{id}`, only for a `DRAFT` or not-yet-started `PUBLISHED` event, hard-deletes + notifies with a self-contained message). `CLOSED` is never deletable.
  - **Timezone bug.** Frontend submitted dates via `.toISOString()` (UTC) while the backend's `LocalDateTime` fields are server-local wall-clock time — shifted every date an hour early during Portuguese summer time, rejecting near-future events as "past." Fixed by submitting the `datetime-local` value as-is.
  - **"Passado" (ended but never closed) wasn't handled anywhere.** A `PUBLISHED` event past its `endDate` stayed fully live: publicly listed, subscribable, and its subscriptions (with `checkedIn` history) still cancellable. Added `endDate < now` checks to the public list query, `subscribe`, and `unsubscribe`; `Event.jsx`/`MySubscriptions.jsx` now reflect real status/dates instead of guessing from dates alone.
  - **Status state machine.** `update()` had no restriction on which status transitions were legal, so a `PUBLISHED`-with-subscribers event could be force-deleted via `PUT status:DRAFT` → `DELETE` (bypassing every timing rule above), and a `CLOSED` event could be reopened the same way. Fixed by forbidding `CLOSED → {DRAFT, PUBLISHED}` and `PUBLISHED → DRAFT` when the event has subscribers (zero-subscriber un-publish stays legal — an earlier unconditional block was a real regression caught in manual testing). `EventEdit.jsx`'s status dropdown mirrors the rule.
  - **Auth entry point bug.** `SecurityConfig` never set an explicit `authenticationEntryPoint`, so Spring Security's default (`Http403ForbiddenEntryPoint`) returned `403` for any missing/expired/invalid token instead of `401` — silently disabling `axiosConfig.js`'s refresh-on-401 flow for natural token expiry. Found via manual testing (a tab left open long enough for a token to expire); fixed with an explicit `401` entry point. Wrong-role `403`s are a separate, unaffected code path.
  - Smaller fixes from the same sweep: capacity can't be reduced below the current subscriber count; rescheduling a `PUBLISHED` event's dates now notifies subscribers; re-uploading an event image deletes the previous file instead of orphaning it.

  Nothing here changes Milestone 3's scope.

## Milestone 3 — Volunteer experience

Volunteers currently only have a flat event list and "my subscriptions" — no personalization or follow-through.

- [x] **New page: Volunteer Dashboard** — upcoming subscribed events, past events attended, total hours volunteered (built on Milestone 2's check-in data)
- [x] Feature: email notifications — signup confirmation, reminder before an event starts, cancellation notice if a promoter closes an event
- [x] Feature: keyword search across event title/description (current filters are location/date/type only)
- [x] Feature: favorite/bookmark an event without subscribing to it
- [x] **New page: public event detail page** — viewable without login (read-only), prompting sign-in only when the user tries to subscribe — improves shareability
- [x] **Milestone review**: confirm every task above is checked off; re-read the milestone against the current code and note anything that needs to change before moving to Milestone 4

  **Review notes (2026-08-08):** All five feature tasks shipped and verified (backend: 40 new MockMvc/unit tests across `SubscriptionControllerTest`, `EventControllerTest`, `FavoriteControllerTest`, `ApiExceptionHandlerTest`, `EmailNotificationTest`, `EmailServiceTest`, `EventReminderSchedulerTest` — 113/113 total; frontend: 21 new Vitest/RTL tests — 59/59 total). Implementation choices, scoped down from the broadest possible version of each task:
  - **Volunteer Dashboard**'s "hours volunteered" is computed in Java (`Duration.between(startDate, endDate)`), not JPQL/SQL — avoids H2/Postgres date-diff dialect differences, the same portability trap V4's split `ALTER TABLE` already hit once. Hours only count subscriptions with `checkedIn=true`; registering without the promoter confirming attendance contributes zero — confirmed explicitly with the user before implementing.
  - **Favorites** got a dedicated `Favorite` entity/table (mirrors `Subscription`'s unique-pair shape, V6 migration) rather than reusing `subscriptions` with a flag — a bookmark has no status/date/capacity restriction at all (deliberately, unlike subscribing), so conflating the two models would have meant the capacity/state-machine guards leaking into a feature that's supposed to be commitment-free. Ships with a dedicated "Os meus favoritos" list page (`/favorites`) — a toggle nobody can browse back to isn't usable end-to-end.
  - **Two real pre-existing bugs found and fixed as part of this milestone**, both required for the public event page to work at all:
    - `EventController.delete()` never cleaned up a `favorites` row before deleting the event — would have thrown an FK violation the first time anyone deleted an event they'd favorited. Fixed alongside adding favorites (`favoriteRepo.deleteByEventId`), covered by `deletingAnEventWithFavoritesButNoSubscribersSucceeds`.
    - `axiosConfig.js`'s response interceptor didn't check whether a `refreshToken` existed before reacting to a 401 — an anonymous visitor triggering any authenticated-endpoint 401 (e.g. `isSubscribed`) caused a doomed refresh attempt ending in a hard `window.location.href = "/login"` redirect, bypassing React Router. This silently made a public event page impossible regardless of the route itself being public. Fixed with an early check; `main.jsx`'s `events/:id` route also had to be pulled out of `ProtectedRoute` (a separate, independent blocker).
  - **Email is entirely best-effort and log-only in dev/test** — gated behind `app.mail.enabled` (default `false`), so `spring-boot-starter-mail`'s autoconfiguration never needs a real SMTP server to boot or to pass tests; a `MailException` never propagates past `EmailService`. Cancellation emails fire on *both* "Encerrar" and "Cancelar" (not just literally "close," per the milestone bullet's wording) — confirmed with the user, since both already trigger the equivalent in-app notification.
  - **Reminder scheduling** added `@EnableScheduling` + a new `EventReminderScheduler` (`app.mail.reminder-cron`, default every 15 min; `app.mail.reminder-window-hours`, default 24h) — no prior scheduling infra existed. Dedup via a new `reminder_sent_at` column on `subscriptions` (V7) rather than a separate tracking table; explicitly reset to `null` on reschedule (`EventController.update`'s existing reschedule branch) so a volunteer already reminded for the old time still gets reminded for the new one.
  - **Public event page**: `Event.jsx` itself became the public page (not a separate component) — `GET /events/{id}` was already `permitAll()`, so no backend change was needed for the read side. Anonymous visitors get a sign-in CTA in place of the subscribe/favorite actions instead of a button that would 401. `Navbar.jsx` gained a minimal anonymous variant (logo + "Entrar") instead of rendering nothing, per the shareability goal.
  - Nothing discovered here changes Milestone 4's scope as written.

## Milestone 4 — Production readiness (no deploy)

Nothing gets deployed to a cloud host in this milestone — the goal is a demo-ready, production-like configuration running entirely locally.

- [x] Dockerize backend and frontend (`Dockerfile` for each) and wire up `docker-compose.yml` for local Postgres + backend (`prod` profile) + frontend (nginx) — one command gives a production-like demo, and is the first time the Postgres path (vs. H2-only) actually gets exercised
- [x] CI pipeline (GitHub Actions): run backend tests + frontend lint/tests on every push/PR — no deploy step
- [x] Make CORS origins and the frontend's API base URL configurable via env vars instead of hardcoded, so the same build works in dev and in the compose demo
- [x] Add a safe generic 500 handler (no stack-trace/message leaks) and a frontend `ErrorBoundary` (no more blank white screen on an unexpected render error)
- [x] Basic structured logging (clear console pattern + rolling file appender under the `prod` profile) and a minimal Spring Boot Actuator `/health` endpoint — no third-party error-tracking service
- [x] Demo polish: branded page title/favicon/meta description (was still default Vite boilerplate), expanded `README.md` covering both the plain-dev and docker-compose paths
- [x] **Milestone review**: confirm every task above is checked off; re-read the milestone against the current code and note anything that needs to change before calling the roadmap done

  **Review notes (2026-08-12):** All six tasks shipped and verified — not just by test suites, but by an actual `docker compose up --build` run against real Postgres 16, the user's own manual click-through of the running demo, and a follow-up independent adversarial review pass — which together surfaced six real bugs beyond what code review or the H2-based test suite alone caught (backend: 122 tests, including 7 new — generic-500-handler body-leak check, CORS-origins-configurability check, date/combined/no-filter query-logic checks, two `ApiExceptionHandler` integration regressions; frontend: 61 tests, including new `ErrorBoundary.test.jsx`; both suites green). Implementation choices and bugs found:
  - **Deploy was explicitly descoped** at the user's request — the original version of this milestone bundled Dockerization/CI with an actual Railway/Render/Fly.io + Vercel/Netlify deploy and hosting-provider secrets management. All of that is now out of scope; secrets stay in a local, gitignored `.env` (`.env.example` tracked with placeholders).
  - **Found and fixed a real latent boot-failure bug**: `application-prod.yml` binds `spring.mail.host/username/password` from env vars with no defaults, and `spring-boot-starter-mail`'s autoconfiguration resolves them eagerly at context startup regardless of `app.mail.enabled` — the container wouldn't boot without them. Fixed with dummy fallback values in `docker-compose.yml`'s environment block (real sends already no-op safely via `EmailService`'s existing try/swallow).
  - **Found and fixed a container permissions bug**: the backend `Dockerfile`'s non-root `spring` user could write `app.jar` (explicitly `chown`'d) but not `/app` itself, so the new rolling-file logback appender couldn't create `logs/` and the container crashed on boot. Fixed by `chown -R spring:spring /app` (and pre-creating `logs/`) before the `USER spring` switch.
  - **Found and fixed the same class of permissions bug a second time, for `/app/uploads`**: same root cause as `logs/` — Docker auto-creates a named volume's mount point as `root:root` if the image never had that directory, and the non-root `spring` user then can't write to it. Since `docker-compose.yml`'s `backend_uploads` volume mounts at `/app/uploads` (never pre-created in the Dockerfile, unlike `logs/` which was already fixed), every event image upload failed silently at the filesystem level. Found via the user reporting "i can't upload images" while clicking through the live demo — not by any test. Fixed by also pre-creating `/app/uploads` in the Dockerfile; the *already-existing* named volume (created before the fix, so still root-owned) had to be explicitly removed and recreated (`docker volume rm v-link_backend_uploads`) — rebuilding the image alone doesn't retroactively fix an existing volume's ownership.
  - **Found and fixed a health-check false-negative**: Actuator auto-registers a `MailHealthIndicator` whenever `spring-boot-starter-mail` is on the classpath, and it live-connects to the configured SMTP host — which is a deliberately-unreachable placeholder in this demo. That dragged `/actuator/health` to `DOWN` even though the app itself was fine, which in turn meant the Docker `HEALTHCHECK` never passed. Fixed with `management.health.mail.enabled: false` — mail is already best-effort everywhere else in the app, so it shouldn't gate overall health either.
  - **Found and fixed a real regression introduced by this milestone's own generic-500 handler**: a bare `@ExceptionHandler(Exception.class)` in `ApiExceptionHandler` intercepts *before* Spring's own default resolution of well-known MVC exceptions (bad JSON, unmapped routes, etc.), so a malformed request body that should 400 was instead swallowed into a misleading generic 500. Caught by an end-to-end smoke test through the live compose stack, not by any unit test. Fixed by having `ApiExceptionHandler` extend `ResponseEntityExceptionHandler` (so those exceptions resolve correctly again) and converting the two existing handlers that collided with it (`MethodArgumentNotValidException`, `MaxUploadSizeExceededException`) from new `@ExceptionHandler` methods into proper `@Override`s of the superclass's dedicated hooks — a second `@ExceptionHandler` for a type the superclass already claims throws an ambiguous-mapping `BeanCreationException` at startup.
  - **Found and fixed a genuinely pre-existing bug, only surfaced by real Postgres — twice, because the first fix was incomplete**: `EventRepository.findByFilters` (the public event list, backing `GET /events`) checks each optional filter with a bare `:param IS NULL`, which gives Postgres's parser no syntactic type to infer for that parameter — a `%param%` embedded in `LOWER(CONCAT(...))` at least gets inferred as `bytea` (still wrong, but a type), while a parameter used in `IS NULL` alone gets none at all. The first fix only cast `:location`/`:keyword` inside their `CONCAT`, which resolved the immediately-reported `lower(bytea)` error — but left every filter's *own* `IS NULL` check uncast. Once Postgres's JDBC driver (`prepareThreshold`) switched this exact repeated SQL to a server-side prepared statement, its Describe step demanded every parameter resolve to a concrete type up front and threw `could not determine data type of parameter $n` — this time on the `date` filter specifically, caught live by the user testing the demo a second time after the first fix shipped. H2 has no equivalent server-side-prepare step, so neither issue was ever visible to the (H2-only) test suite. Fixed properly this time: `CAST(:param AS ...)` on every occurrence of `location`/`date`/`type`/`keyword`, including the bare `IS NULL` checks — verified by firing the same query 12+ times against live Postgres (well past the threshold) with every filter and every combination.
  - **Found and fixed a stale-cache risk via an independent review pass**: `frontend/nginx.conf` set a 7-day `expires` header for hashed static assets but nothing for `index.html` itself — since Vite hashes JS/CSS filenames on every build but `index.html`'s URL never changes, a cached copy of it (browser heuristic caching, a corporate proxy, a future CDN) could keep referencing asset filenames a newer deploy already deleted, breaking the app until a hard refresh. Fixed with an explicit `location = /index.html { add_header Cache-Control "no-cache"; }`; verified the header split is correct (`index.html` → `no-cache`, a real hashed asset → `max-age=604800`) against the live compose stack. Not found by any test — a second full review pass (deliberately adversarial, checking claims against a running Postgres/Docker container rather than just reading code) is what caught it, after the first review pass's fixes were already believed complete.
  - **Rate limiting stays in-memory/single-instance** (`LoginAttemptService`) — moving to something shared (Redis) would only matter for a real multi-instance deploy, which isn't happening here. Documented as an accepted limitation, not fixed.
  - **No Sentry or other third-party error-tracking** — confirmed with the user; structured logging (console + prod-profile rolling file) plus the now-correct generic 500 handler covers "failures are visible" without an external account.
  - Nothing discovered here changes the roadmap — this was the last planned milestone. Actual deployment, if/when wanted, would need its own scoping pass (hosting choice, real secrets management, HTTPS, CORS origin for the real domain).

## Milestone 5 — Free deployment (demo)

Actually deploys V-Link, for the first time, as a free, low-traffic portfolio/demo link — explicitly **not** a production launch for real promoters/volunteers. Every tool and tradeoff below was stress-tested against that framing before being picked; several free-tier facts changed since Milestone 4's "deploy would need its own scoping pass" note, so nothing here was assumed from stale knowledge.

**Scoping decisions (2026-09-10):**
- **Stack: Vercel (frontend) + Render (backend) + Supabase (Postgres + Storage).** Fly.io and Railway no longer have workable free tiers (Fly requires a card with no free allowance for new accounts; Railway is trial-credit-only) — Render is effectively the only remaining free host for a persistent, Dockerized JVM backend. Best-of-breed beats a single platform for everything: Render's own free Postgres self-destructs 30 days after creation, so the database was never going to stay on the same platform as the backend regardless.
- **Email is off for this deploy — Brevo was dropped entirely.** Brevo's free plan can't authenticate a sender against a free email domain (@gmail.com etc.) — messages get rejected or spam-filtered without owning a domain to authenticate, which conflicts with the "free subdomains only, no domain purchase" decision below. Rather than ship email that half-works into spam folders, `app.mail.enabled` is forced off via a new env var; in-app notifications are unaffected.
- **No custom domain.** Free `*.onrender.com` / `*.vercel.app` subdomains only — a domain costs real money annually, which breaks the "fully free" constraint. CORS and API base URL are pinned to these subdomains.
- **Accepted, documented limitations, not fixed:**
  - Render's free web service sleeps after 15 min idle (30–50s cold start on the next request).
  - Render's free tier caps at 512MB RAM — tight for Spring Boot even after JVM tuning; real-world reports show OOM under load is possible even tuned. Acceptable given expected traffic is a personal-project link, not real users.
  - Supabase's free project pauses after 7 days of zero DB activity, with no auto-resume (unlike Neon) — mitigated with a weekly keep-alive ping, not eliminated.
  - `EventReminderScheduler` only runs while Render is awake; reminders can lag behind a sleeping instance.
- **Supabase Storage keep-alive uses a raw SQL ping (`psql ... SELECT 1`), not Supabase's REST/anon-key API.** The backend has never used Supabase's client SDK or REST layer — none of the tables have Row Level Security policies. Pinging via the anon-key REST API would risk exposing tables like `users` (password hashes included) through an API surface nobody meant to enable. The raw SQL ping reuses the same DB credentials already needed for deploy, with no new key.
- **`FileStorageService` is being migrated to Supabase Storage for `prod`, not left as ephemeral local disk.** This was the one genuinely large code change in this milestone (new interface, new S3-compatible implementation, new test, new secrets) — a deliberate choice to have uploaded event images survive Render redeploys/restarts, at the cost of real implementation work versus every other item here being config/YAML.

- [x] Provision a Supabase project (Postgres + a public Storage bucket); grab the pooled connection string (`sslmode=require`) and S3-compatible access keys
- [x] Provision Render (backend, free web service deploying the existing `backend/Dockerfile`) and Vercel (frontend, native Vite build — no Docker/nginx for this path)
- [x] Split `FileStorageService` into an interface, with `LocalFileStorageService` (dev/test, unchanged behavior) and a new `SupabaseFileStorageService` (S3-compatible API via the AWS SDK, `forcePathStyle=true`, public bucket); add a test for the new implementation with a mocked S3 client
- [x] Parameterize `app.mail.enabled` in `application-prod.yml` behind `APP_MAIL_ENABLED` (default `true`, so `docker-compose.yml`'s existing local demo is unaffected) so Render can set it to `false`
- [x] Add JVM heap tuning (`JAVA_OPTS`/`-Xmx`) to the backend Dockerfile's entrypoint for Render's 512MB free-tier cap
- [x] Wire real env vars end to end: `app.cors.allowed-origins` → the Vercel URL, `VITE_API_BASE_URL` → the Render URL, `DB_URL`/`DB_USERNAME`/`DB_PASSWORD` → Supabase, `JWT_SECRET`, dummy `MAIL_HOST`/`MAIL_USERNAME`/`MAIL_PASSWORD` placeholders, `APP_STORAGE_PROVIDER=supabase` + Supabase Storage project URL/bucket/S3 keys

- [x] **Milestone review**: confirm every task above is checked off; smoke-test the live deploy end to end (register/login, create + publish an event, subscribe, check in, image upload survives a redeploy, organizer dashboard) before calling it done

  **Review notes (2026-09-11):** Live at `https://v-link-bbkp.onrender.com` (backend) and `https://v-link-pearl.vercel.app` (frontend), backed by a real Supabase project. Full flow verified against the live deploy, not just locally: register/login, create + publish an event, image upload to Supabase Storage, image survives independently of the app (fetched directly, and re-verified after a redeploy), and event deletion cleans up its image. CI's `deploy` job was watched running for real (not just written) — it only fires after `backend`+`frontend` pass, and both deploy hooks were confirmed to actually trigger builds. Most of this milestone's actual work happened *after* first going live — the plan's own design decisions held up, but three real bugs only existed at the intersection of this code and Supabase's actual infrastructure, and none of them were visible from local testing, mocked unit tests, or a healthy-looking deploy:

  - **Postgres pooler incompatibility (real, serious — first deploy attempt flatly failed).** Flyway's own migration transaction threw `ERROR: prepared statement "S_1" already exists` against Supabase's transaction-mode pooler (port 6543, Supavisor) — pgjdbc's server-side prepared statements assume the same physical connection persists across a session, but transaction-mode pooling can route each query to a different backend connection. This is the same underlying pgjdbc behavior (`prepareThreshold`) already documented elsewhere in this file for `findByFilters`, showing up in a new context. Fixed by appending `prepareThreshold=0` to `DB_URL`, which disables server-side prepared statements entirely — the standard fix for this exact PgBouncer/Supavisor-plus-JDBC combination. H2 has no pooler equivalent, so this was never visible to the test suite, same lesson as the earlier `findByFilters` bug.
  - **Wrong S3 endpoint domain (real, would have permanently broken uploads).** `SupabaseFileStorageService` originally built the S3-compatible endpoint on the plain `<ref>.supabase.co` domain — Supabase's docs (checked only after the live failure, not before writing the code) specify a *separate* `<ref>.storage.supabase.co` subdomain for the S3 API. This one is a real lesson about the local Docker smoke test's blind spot: constructing the `S3Client` with fake credentials and never calling it doesn't catch a wrong endpoint at all, since the SDK builder never validates the URL until a real network call is attempted — "boots clean" and "the S3 config is correct" turned out to be unrelated facts.
  - **`ListObjectsV2`-by-prefix + batch `DeleteObjects` don't reliably work against Supabase Storage's gateway (real, silent data-cleanup bug).** The original `deleteEventImages` listed objects under `events/{id}/` and batch-deleted the results, mirroring `LocalFileStorageService`'s folder-delete — confirmed live that `ListObjectsV2` doesn't reliably find an object that a direct GET/DELETE by key can still reach, and the batch `DeleteObjects` operation errors outright on this gateway. Both failures were silent, wrapped in the same best-effort catch used everywhere else in this class (deliberately, so a Storage hiccup never blocks deleting the event record) — meaning deleted events would have quietly left orphaned images in the bucket forever, discovered only by directly checking Supabase Storage after a delete looked successful. Fixed by dropping the list/batch-delete approach entirely: since an event has at most one live image at a time, `deleteEventImages` now takes the already-known current image URL and deletes that single key directly, the same proven path `deletePreviousImage` already used. `FileStorageService`'s interface signature changed (`deleteEventImages(Long, String)`) to carry that URL through — a real interface change made after first going live, not part of the original design.
  - **False alarm, not a real bug: a local test-script bug initially looked exactly like a hung production S3 call.** `curl -F "file=@/c/Users/.../tiny.png"` from Git Bash on Windows silently fails to open the file when passed to curl's Windows-native binary (POSIX-style path, not translated) — combined with `-s` (silent), this produces `HTTP:000` with zero error output, indistinguishable at a glance from a genuinely hung server-side request. This cost real debugging time (bounding the S3 client's timeout, suspecting Render's network, checking Render's own deploy-swap behavior) before the actual `curl: (26) Failed to open/read local data from file` message surfaced by accidentally piping verbose output differently. Lesson for next time testing from this shell: use a native Windows-style path (`C:\Users\...`) in any `curl -F @path` call, and never combine `-s` with a new/unverified command — silent mode hides exactly the signal needed to tell "client bug" from "server bug" apart.
  - **Cosmetic, not a bug:** every deploy's boot log shows a `SpringApplicationShutdownHook`-driven graceful shutdown a few seconds after the app's first successful request, followed by Render's "Your service is live" banner — happens identically on every single deploy regardless of what changed, consistent with Render's own free-tier deploy-verification mechanics rather than anything in this app. Never affected reachability once settled; not investigated further since there was nothing actionable to fix.
  - **Also confirmed, not initially obvious:** a public Supabase Storage object URL can still return `200` for a short window immediately after the underlying object is actually deleted (CDN edge-cache staleness) — verified the real state via a direct `HeadObject` S3 call (404) rather than trusting the public URL's response as ground truth.
  - Render's free-tier boot time for this app is consistently ~195-205 seconds (cold JVM + Hibernate + Flyway against Postgres, throttled free-tier CPU) — several times longer than the local Docker smoke test's ~17 seconds. Nothing to fix (this was an accepted, documented limitation going in), just a concrete number worth having on record for next time something looks "stuck" mid-deploy.
  - Nothing here changes the roadmap — this was the last planned milestone.

## Milestone 5 addendum — Performance hardening (2026-09-11)

A follow-up pass, prompted by collecting real production performance numbers (for a CV, not a product requirement) and then fixing what the numbers turned up. Same rule as everywhere else in this file: every fix below was validated by a real before/after measurement against the live deploy, not assumed from the code alone.

- **SPA-fallback routing bug on Vercel (real, broke the app for any real visitor).** Any direct navigation or hard refresh on a non-root frontend route (`/events`, `/login`, `/dashboard`, a shared `/events/{id}` link, ...) returned Vercel's own `404 NOT_FOUND` instead of `index.html` — nothing told Vercel to let React Router handle unmatched paths client-side. Only `/` worked. This broke the shareable public event link (the whole point of Milestone 3's public event page) and any bookmark/reload anywhere else. Fixed with a `rewrites` rule in `frontend/vercel.json` (`{"source": "/(.*)", "destination": "/index.html"}`), scoped to that file only — `git.deploymentEnabled` and the docker-compose `nginx.conf`'s cache-control split are untouched. Verified live: `/events`, `/login`, `/events/{id}`, `/dashboard` all went from `404` to `200` with real SPA content, including a simulated hard refresh (`Cache-Control: no-cache`).
- **`GET /events` N+1 query (real, dominated latency even at low load).** `EventController.getEvents()` called `subscriptionRepo.countByEventId()` once per event in the list — invisible on loopback H2/local Postgres, but the Render↔Supabase cross-region round trip (Frankfurt / `eu-north-1`) made this the dominant cost of the endpoint: p95 was 1754ms at just 10 req/s, vs. ~647ms for `GET /events/{id}` (same load, no N+1). Fixed with a single batched `GROUP BY event_id` query (`SubscriptionRepository.countByEventIds`), merged in Java; `GET /events/{id}`, `/mine`, `create`, `update`, and image upload were untouched (only the list had the N+1). Verified: counts cross-checked against `GET /events/{id}` for 3 events (exact match), and a clean re-measurement at 10 req/s dropped p50 1035→593ms, p95 1754→975ms, p99 2052→1193ms (~43-44% down, isolated from the HikariCP change below by testing this fix alone first).
- **HikariCP pool size vs. Render's default (real, was directly causing full-service crashes).** Spring Boot's default pool (10) combined with the default 30s `connectionTimeout` let 50 req/s of sustained load queue up faster than connections could drain — confirmed via Render logs, reproduced twice independently as full crashes (`HikariPool-1 ... timed out after 30000ms, total=10, active=10`), each needing a ~190-210s auto-restart. Before raising the pool, checked Supabase's actual `max_connections` directly (`SHOW max_connections` → 60, ~21 already held by Supabase's own internal roles, ~39 free) so the fix wouldn't just move the bottleneck into Postgres. Set `maximum-pool-size: 20` and `connection-timeout: 5000` (fail fast instead of queueing for 30s). **Partial win, reported honestly:** `GET /events` at 50 req/s no longer crashes the service (432/1500 succeeded, real failures now, not an outage) — a full curve was measured after the fix: clean up to ~20 req/s, degrading from ~30 req/s, badly degraded but *not crashing* by 50 req/s. **`POST /auth/login` still crashes the service, even at 10 req/s post-fix** — its bottleneck is BCrypt's CPU cost under Render's throttled free-tier CPU, a completely different resource than the DB pool this fix addresses; raising Hikari further would not help. Not fixed here — out of scope of what was asked (HikariCP only), left as a known, documented limitation.
- **Lighthouse "`/events`" scores were actually the Login page's scores (methodology bug in the testing itself, not an app bug).** `/events` (the plural list page, `EventList.jsx`) is wrapped in `ProtectedRoute`, which client-side-redirects an anonymous visitor to `/login` via React Router's `<Navigate>` — this is deliberate, not a bug (only `/events/:id`, the single-event detail page, is meant to be public). Lighthouse's `finalUrl` field doesn't detect a `history.pushState`-based redirect (it only tracks real network navigations), so it kept reporting the requested URL even though the page it actually audited was the Login form. Caught by directly checking `window.location.href` after page-load with Puppeteer, independent of Lighthouse. Re-ran Lighthouse against the two real public pages (`/` and `/events/{id}`) plus, using a Puppeteer-driven real login (so the auth token lands in `localStorage` the same way a real user's would), the authenticated promoter dashboard.
- **Two small, real, unrelated accessibility bugs found while investigating the above** (Lighthouse accessibility scores of 91–96 across pages prompted a closer look): `Login`/`Register`'s show/hide-password `IconButton` had no `aria-label` at all; and `Landing`/`Login`/`Register` render outside the shared `App` layout (the only place with a `<main>` landmark), so none of the three pages had a `<main>` landmark. Both fixed (aria-labels added; `component="main"` added to each page's own outer `Box`). `Login.test.jsx`'s `getByLabelText("Password", { exact: false })` needed `{ selector: "input" }` added — the new aria-label also contains "password", so the old query started matching two elements.
- **`EventList.jsx`'s `useEffect` missing-dependency lint warning fixed properly, not suppressed.** `fetchEvents` was a plain inline function (new identity every render) called from an effect whose deps array only listed `[filters]` — functionally correct (the effect always calls that render's fresh closure), but ESLint can't prove that statically. Wrapped `fetchEvents` in `useCallback(..., [filters])` and added it to the effect's deps instead of an eslint-disable comment — zero behavior change (same existing debounce test still passes unmodified), and the warning is gone from CI for real.
- **Color-contrast findings surfaced by the same Lighthouse investigation, not yet fixed — a design decision, not applied unilaterally:** three status chips in `OrganizerDashboard.jsx` (`STATUS_STYLE`) and the role chip in `Navbar.jsx` fall short of WCAG AA's 4.5:1 for normal text (`PUBLISHED` chip 2.97:1, `DRAFT` chip 3.05:1, `CLOSED` chip 4.37:1, role chip 4.04:1), as does the `#E53E3E` destructive-button/text red used across `OrganizerDashboard.jsx`/`MySubscriptions.jsx`/`Navbar.jsx` (4.13:1 on white). Passing replacements computed (same hue family, WCAG contrast formula, checked against each element's actual rendered background including its opacity tint): `PUBLISHED` → `#0F7A3D` (4.88:1), `DRAFT` → `#8A5F1F` (5.13:1), `CLOSED` → `#52525B` (6.99:1), role chip gold → `#E8C179` (5.23:1), destructive red → `#C62828` (5.62:1). Not applied — this changes visible brand colors, a call for whoever owns the brand palette, not something to change unprompted.
- **Production cleanup:** the perf-testing pass above created 35 test users, 4 events, 2 subscriptions, and (from all the repeated logins) 228 `refresh_tokens` rows in the live Supabase database (`deploy-smoke-*`, `final-verify-*`, `perf-*@example.com` — inventoried first, confirmed zero real user data mixed in, then hard-deleted in FK-safe order directly against Postgres). `GET /events` on the live API now correctly returns `[]`.
- Nothing here changes the roadmap.
